# Портал школьного конкурса «Мы помним связь поколений»

Полное техническое описание проекта: постановка задачи, архитектура, выбор технологий,
устройство бэкенда и фронтенда, деплой, ограничения и пути развития.

Репозиторий: `github.com/Vatislo/svyaz-pokoleniy`
Лайв-адрес: `https://svyaz-pokoleniy.onrender.com`

---

## 1. О чём проект

«Связь поколений» — портал школьного конкурса памяти, посвящённого Великой
Отечественной войне. Школьники загружают сюда материалы: фотографии семейных
историй, снимки памятных мест, экскурсии по музеям, видеоролики, буктрелеры,
пары «тогда/сейчас». Материалы проходят модерацию и попадают в публичный
архив, который можно листать, фильтровать и изучать.

Портал закрывает три роли:

- **Участник** — находит на главной призыв к участию, заполняет многошаговую
  форму, прикладывает файлы и отправляет работу на проверку.
- **Посетитель** — смотрит каталог одобренных работ, фильтрует по разделам,
  типам материала и тегам, открывает карточку проекта с галереей, видео,
  слайдером «тогда/сейчас».
- **Администратор** — входит в защищённую админку, видит очередь заявок,
  одобряет/удаляет/восстанавливает проекты, редактирует карточки, удаляет
  мусор безвозвратно.

Полный цикл: *участник отправил → администратор проверил → опубликовано →
посетители смотрят*. Без участия программиста после первоначального развёртывания.

## 2. Постановка задачи

### Проблема

Школьные конкурсы памяти существуют в двух крайностях: либо пост в соцсети,
который утонет в ленте через неделю, либо «тяжёлый» сайт на типовом конструкторе,
где неудобно модерировать и нельзя показать фото «до/после». Материалы
распадаются по чатам, нет единого архива, нет контроля публикации.

### Цель

Единый портал конкурса: публикация материалов участниками, модерация
администратором, публичный тематический архив. Разворачивается одной командой,
управляется через браузер, не требует серверного «хозяйства» от школы.

### Функциональные требования

1. Главная страница-лендинг со сценарной подачей (обложка → разделы →
   «тогда/сейчас» → история → призыв к участию).
2. Каталог одобренных проектов: поиск, фильтры по разделам, типам и тегам,
   счётчик найденного, случайный материал.
3. Страница проекта: описание, теги, основной материал по типу (фото,
   галерея до 12 фото, видео, GIF, сравнение «тогда/сейчас», файл),
   сведения об авторе, соседние и похожие проекты.
4. Форма отправки: 3 шага, 6 типов материалов, 6 тем, теги, дата или период,
   согласие на публикацию, живой предпросмотр карточки.
5. Админка: вход по паролю, очередь заявок, одобрение/удаление/восстановление,
   инлайн-редактирование карточки, безвозвратное удаление.
6. Светлая/тёмная тема, адаптивная вёрстка, доступность (клавиатура, скринридер).

### Нефункциональные требования

- Развёртывание без установки СУБД на сервере пользователя.
- Один домен для сайта, админки и API (без CORS-головной боли).
- Первый запуск «с нуля» автоматически создаёт схему, наполняет базу
  демоданными и заводит администратора.
- Валидация файлов и полей на сервере (не доверяем клиенту).

## 3. Архитектура

Классический **трёхзвенный монолит** в одном Node.js-процессе:

```
Браузер
  │  HTTPS
  ▼
Express (server/index.js, порт 3001)
  ├── статика dist/          ← собранный React-билд (сайт + админка)
  ├── /uploads/*             ← локальные файлы (legacy, multer diskStorage)
  ├── /api/*                 ← REST API, JSON
  │     ├── публичные маршруты (проекты, логин)
  │     └── /api/admin/*     ← только при живой сессии администратора
  ▼
Данные
  ├── локально:   SQLite-файл server/data/app.db + server/uploads/
  └── на Render:  Turso (облачная SQLite) + Cloudinary (файлы)
                  — переменные TURSO_URL / CLOUDINARY_URL,
                    без них сервер работает с локальным диском
```

Такое переключение «по переменной окружения» — сознательное решение:
бесплатный Render стирает локальный диск при каждом рестарте, поэтому
постоянное хранение вынесено в два независимых внешних сервиса, а код
адаптируется автоматически: заданы ключи — данные в облаке, не заданы —
работает как раньше (локальная разработка, тесты).

Почему монолит, а не «SPA на Pages + отдельный API»:

- школьному порталу не нужна горизонтальная масштабируемость, нужна
  простота развёртывания и одна ссылка во всех материалах;
- куки сессии администратора и API живут на одном origin — не нужны CORS,
  SameSite-костыли и отдельный домен для бэкенда;
- деплой — один сервис, одна точка сборки, меньше что ломается.

В **dev-режиме** звенья разведены: Vite (5173) раздаёт фронтенд с HMR и
проксирует `/api` и `/uploads` на Express (3001) — `npm run dev:all`.
В **production** Vite не участвует: Express раздаёт готовый `dist/` и,
кроме `/api/` и `/uploads/`, любой GET-запрос получает `index.html`
(SPA-fallback), так что прямые ссылки работают.

### Структура репозитория

```
src/                    фронтенд (React)
  pages/                Home, Catalog, ProjectDetail, NewProject, Admin
  components/           Header, SiteFooter, PublicProjectCard, CompareSlider,
                        MediaLightbox, SafeImage, ui/ (примитивы shadcn)
  lib/                  router.js, theme.js, api.js, useSnapScenes.js
  data/content.json     весь редактируемый текстовый контент
server/                 бэкенд (Express)
  index.js              приложение, маршруты, загрузки, раздача dist
  db.js                 libSQL/SQLite-адаптер под API mysql2
                        (локальный файл или Turso по TURSO_URL)
  init.js               CREATE TABLE, seed, создание администратора
  seed.sql              стартовые проекты
  setup.js              npm run setup
  create-admin.js       создание/сброс пароля админа
  migrate-from-mysql.js разовая миграция из старой MySQL-базы
  import-live.js        перенос проектов и файлов с живого сайта
render.yaml             конфигурация деплоя на Render (Blueprint)
```

## 4. Стек и обоснование выбора

| Слой | Технология | Почему именно она |
|---|---|---|
| UI | React 18 | Компонентная модель, де-факто стандарт, команда школы быстро осваивает |
| Сборка | Vite 6 | Мгновенный dev-сервер и HMR, ультимативно быстрый билд, ноль конфигурации по сравнению с Webpack |
| Стили | Tailwind CSS 4 | Утилитарный CSS, скорость вёрстки, темы через CSS-переменные; v4 подключается как Vite-плагин без отдельного конфига PostCSS |
| UI-примитивы | Radix UI + shadcn/ui | Доступные (aria, фокус-менеджмент, клавиатура) диалоги/переключатели без «чёрного ящика» — код компонентов лежит в проекте и редактируется |
| Роутинг | собственный hash-роутер (~40 строк) | SPA с пятью экранами не оправдывает react-router; hash-маршруты не требуют серверных rewrite-правил при деплое |
| API | Express 5 | Минимализм, middleware-модель, асинхронные обработчики, привычен для учебных проектов |
| БД | SQLite-диалект (libSQL): локальный файл или Turso Cloud | Одна и та же SQL-схема локально и в облаке; файл — ноль администрирования, Turso — постоянное хранение на хостинге без своего сервера СУБД |
| Загрузки | multer 2 | Стандарт для multipart/form-data в Express: лимиты, фильтр типов, diskStorage |
| Пароли | bcrypt 6 | Солёные хэши, cost factor 12; валидный пароль невозможно восстановить из БД |
| Сессии | express-session | Серверные сессии в httpOnly-куке: секретный токен на клиенте, состояние на сервере |
| Хостинг | Render (free) | Деплой из GitHub по push, автоматические HTTPS и порт из окружения, `render.yaml` в репозитории = Infrastructure as Code |

Чего сознательно **нет**: TypeScript (учебный проект, скорость иттераций важнее),
PostgreSQL/MySQL (не нужен объём данных и вычислений), Redis (сессий на
один процесс хватает), Docker (Render собирает из Node-образа без контейнера).

## 5. База данных

### Зачем SQLite

Проект живёт в одном процессе на бесплатном хостинге. SQLite даёт:

- **нулевое администрирование** — нет отдельного сервиса, порта, паролей;
- **простой бэкап** — скопировать один файл `app.db`;
- **переносимость** — локальная разработка и продакшен работают одинаково;
- **переезд в облако без смены SQL** — тот же диалект работает в Turso
  (libSQL-совместимый сервер SQLite), меняется только строка подключения
  в `db.js`: локальный `file:` или `libsql://` по переменной `TURSO_URL`.

Для объёма школьного конкурса (сотни проектов, десятки мегабайт текста)
производительности SQLite более чем достаточно: индекс по `status` +
сортировка по `created_at` обрабатываются за микросекунды.

### Режимы хранения

| Режим | Включается | БД | Файлы |
|---|---|---|---|
| Локальный (dev, тесты) | ключи не заданы | `server/data/app.db` (WAL) | `server/uploads/` |
| Облачный (Render) | `TURSO_URL` + `CLOUDINARY_URL` | база Turso | облако Cloudinary |

Адаптер `db.js` поверх `@libsql/client` сохраняет интерфейс `mysql2/promise`
(`pool.execute` → `[rows]` / `[{insertId, affectedRows}]`), поэтому маршруты
API не знают, где физически лежат данные.

### Схема

```sql
projects (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  title         TEXT NOT NULL,                 -- ≤200 символов (проверка на API)
  description   TEXT NOT NULL,
  author        TEXT NOT NULL,
  email         TEXT NOT NULL,                 -- виден только админу
  image_url     TEXT NOT NULL,                 -- /uploads/<файл>
  status        TEXT NOT NULL DEFAULT 'pending',
  created_at    TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ','now')),
  updated_at    TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ','now')),
  topic         TEXT,                          -- 6 разделов архива
  project_type  TEXT NOT NULL DEFAULT 'photo', -- photo|story|video|gif|pair|other
  media_url     TEXT,                          -- видео/GIF/файл
  before_image_url TEXT, after_image_url TEXT, -- сравнение «тогда/сейчас»
  author_role   TEXT, project_date TEXT, source_info TEXT,
  tags_json     TEXT,                          -- JSON-массив строк
  gallery_json  TEXT                           -- JSON-массив путей
)

admins (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  username TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,                 -- bcrypt
  created_at TEXT
)
```

Триггер `projects_touch`: любой `UPDATE` по `projects` автоматически
обновляет `updated_at`. Приложение об этом не думает — метка всегда актуальна.

Массивы (теги, галерея) хранятся как JSON-строки в TEXT: SQLite не имеет
удобного нативного массива, а глубокая нормализация (таблицы `tags`,
`gallery`) для учебного объёма — over-engineering. На границе API сырые
колонки парсятся в настоящие массивы (`withProjectTags()`), фронтенд получает
чистые объекты.

### Статусы — жизненный цикл модерации

```
         (участник отправил)
                │
                ▼
            pending ──────approve/publish/restore──────▶ approved
                │                                             │
                └──────────── delete/remove ◀─────────────────┘
                                    │
                                    ▼
                                deleted ──── permanent ────▶ (удалено из БД
                                    │         DELETE         и с диска)
                                    └── restore ──▶ approved
```

- публичные эндпоинты отдают **только** `approved`;
- `deleted` — это корзина: восстановима, безвозвратное удаление разрешено
  **только** из неё (защита от случайного «навсегда» по горячей кнопке);
- смена статуса — узкое место прав доступа: выполняется исключительно
  авторизованным администратором.

### Миграция из MySQL

Изначально данные жили в MariaDB (дамп MAMP). Перенос: `npm run migrate:mysql`
читает таблицы через mysql2, конвертирует даты в ISO-8601 (UTC), upsert'ит
строки в SQLite по `id`, копирует администратора вместе с bcrypt-хэшем
(перехэшировать не нужно — формат `$2*` совместим). Файлы `uploads/` лежали
на той же машине — их переносить не требовалось.

## 6. API

REST, JSON, сессионная авторизация (кука `svyaz.sid`).

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| GET | `/api/health` | публичный | пинг для healthcheck хостинга |
| GET | `/api/auth/me` | публичный | состояние сессии (`authenticated`, `username`) |
| POST | `/api/auth/login` | публичный | вход администратора (bcrypt-сравнение, `session.regenerate()`) |
| POST | `/api/auth/logout` | публичный | `session.destroy()` |
| GET | `/api/projects` | публичный | одобренные проекты, новые сверху |
| GET | `/api/projects/:id` | публичный | один одобренный проект (404 для pending/deleted) |
| POST | `/api/projects` | публичный | заявка участника (multipart, до 16 файлов) → `pending` |
| GET | `/api/admin/projects` | админ | все проекты всех статусов |
| PATCH | `/api/admin/projects/:id` | админ | правка карточки (тексты, тема, тип, теги, новая обложка) |
| PATCH | `/api/admin/projects/:id/:action` | админ | `approve`/`publish`/`restore` → approved, `delete`/`remove` → deleted |
| DELETE | `/api/admin/projects/:id/permanent` | админ | безвозвратное удаление (строки + файлы), только из `deleted` |

### Приём файлов

Два взаимозаменяемых движка multer, выбирается по наличию
`CLOUDINARY_URL`:

- **локально**: `multer.diskStorage` в `server/uploads/`, имя файла
  `${Date.now()}-${random8}${ext}` (защита от коллизий и path traversal —
  имя генерирует сервер, originalname не используется);
- **в облаке**: свой StorageEngine на `cloudinary.uploader.upload_stream` —
  файл уходит в Cloudinary, в базу записывается полный `https://`-адрес.

Поля в базе (`image_url`, `gallery_json`…) хранят либо `/uploads/<имя>`,
либо облачную ссылку — фронтенд не различает эти случаи, а удаление
(правка обложки, безвозвратное удаление) идёт через общий хелпер
`removeMediaUrl()`, который понимает оба формата. Старые локальные файлы
по-прежнему раздаются Express-статикой `/uploads`.

Лимиты: 60 МБ и 16 файлов на запрос; допустимы `image/*`, `video/*`,
`audio/*`, `application/pdf`. Обложка — строже: изображение ≤8 МБ;
фото галереи — ≤8 МБ каждое, максимум 12 штук (бесплатный лимит
Cloudinary на изображение — 10 МБ, проект укладывается).

`upload.any()` + таблица псевдонимов полей (`cover` → `image` и т.п.) —
устойчивость к старым клиентам: сервер не падает с «Unexpected file field»,
а понятно отвечает 400 с перечнем допустимых имён. При любом отказе
валидации уже принятые файлы откатываются (`discardFiles()` — unlink
локально или `destroy` в облаке), чтобы не копились сироты.

### Валидация

Всё, что пришло с клиента, перепроверяется на сервере: обязательные поля,
длины строк, допустимые значения `topic`/`project_type`, соответствие типа
материала приложенным файлам (для `video` обязательно видео, для `pair` —
два изображения), нормализация тегов (срез `#`, дедупликация, лимит 20).

## 7. Фронтенд

### Роутинг

Собственный hash-роутер `src/lib/router.js`: хук `useHashRoute()` слушает
`hashchange`, отдаёт путь (`/`, `/catalog`, `/project/:id`, `/create-project`,
`/admin`) — query-параметры парсятся отдельно (`#/catalog?tag=война`).

Hash-роутинг выбран осознанно: прямая ссылка на карточку проекта работает
на любом статик-хостинге без настройки rewrite-правил, а на Render дополнительно
страхует SPA-fallback в Express.

### Страницы

**Главная** — «сценарный» лендинг: конфигурация сцен лежит в `content.json`,
рендерятся из неё. На десктопе включается режим снап-сцен (`useSnapScenes`):
колесо/стрелки/свайп переключают полноэкранные сцены с накоплением пикселей
и локом, скролл внутри сцены и открытые диалоги не перехватываются,
`prefers-reduced-motion` отключает режим. Сцены с контентом («тогда/сейчас»,
примеры проектов) показываются только при наличии реальных данных из API.

**Каталог** — карточки одобренных проектов + клиентская фильтрация:
текстовый поиск по названию/описанию/автору/тегам, мультивыбор разделов
и типов (Radix ToggleGroup), чипы тегов, счётчик с `aria-live`, случайный
материал, пустое состояние со сбросом.

**Проект** — загружает проект и каталог параллельно: второе — для
предыдущего/следующего и блока «похожие» (совпадение по теме или тегам).
Основной материал рендерится по типу: `pair` → `CompareSlider` (ползунок на
pointer-событиях + прозрачный `<input type="range">` для клавиатуры),
`video`/`gif` → лайтбокс, `other` → ссылка на файл, галерея → сетка с
лайтбоксом (клавиатурная навигация, счётчик «N / M»).

**Новый проект** — 3 шага (материал → история → автор), черновик формы
переживает переходы между hash-маршрутами, файлы с превью и удалением,
обязательное согласие на публикацию, сайдбар с живым предпросмотром
карточки. Отправка — `FormData` на `POST /api/projects`.

**Админка** — SPA после входа: фильтры-кнопки pending/approved/deleted со
счётчиками, карточки с файлами, действия модерации, инлайн-редактирование.
E-mail автора показывается только здесь.

### Контент-стратегия

Весь редактируемый текст, названия разделов, сцены главной, пункты меню и
имена в футере вынесены в `src/data/content.json`. Правка текста на сайте =
правка одного JSON-файла без пересборки компонентов. Имена разработчиков и
авторов в футере добавляются записью в массив (пустые имена не выводятся).

### Доступность

Skip-to-content ссылка; `aria-current` для навигации; `aria-live` для счётчика
каталога; `aria-pressed` на фильтрах и переключателе темы; `inert`/`aria-hidden`
на неактивных сценах; лейблы у всех полей формы; `role="alert"` для ошибок;
полная работа слайдера сравнения и лайтбокса с клавиатуры; поддержка
`prefers-reduced-motion`; видимый focus-ring; `SafeImage` — картинка с
доступной заглушкой при ошибке загрузки.

### Тема

Светлая («бумажная»: камень, графит, красный акцент) и тёмная. Тема живёт в
`data-theme` на `<html>` + localStorage; инлайн-скрипт в `index.html` читает
её **до** загрузки React — нет «мигания» белым экраном. Переключатель —
в шапке, состояние синхронизировано через CSS-переменные.

## 8. Безпарольная безопасность (Security posture)

- **Пароли**: bcrypt, cost 12; пароль администратора — только в переменной
  окружения, минимум 12 символов; в БД лежит только хэш.
- **Сессии**: httpOnly-кука (JS не читает), `sameSite=lax`, `secure=auto`
  (включается на HTTPS), срок 24 ч; на входе — `session.regenerate()`
  (защита от фиксации сессии); секрет — из `SESSION_SECRET`.
- **Доверие прокси**: `app.set('trust proxy', 1)` только в production —
  иначе Express не увидит `X-Forwarded-Proto` и secure-куки сломаются.
- **Uploads**: имя файла генерирует сервер; mimetype фильтруется;
  размеры и количество ограничены; каталог вне корня статики.
- **Права админа**: каждый `/api/admin/*` проходит `requireAdmin`;
  безвозвратное удаление — только из статуса `deleted`.
- **Не доверяем клиенту**: все ограничения формы повторены на сервере.
- **Секреты**: `server/.env` в `.gitignore`; на Render — переменные окружения
  (секреты генерируются при создании сервиса).

## 9. Деплой

### Локально

```bash
npm install
npm run setup      # .env, таблицы, seed, администратор
npm run dev:all    # сайт 5173 + API 3001
```

### Прод (Render + GitHub)

Код лежит в GitHub, деплой описан `render.yaml` (Blueprint):

- build: `npm install && npm run build`;
- start: `npm start` (NODE_ENV=production);
- `PORT` берётся из окружения (сервер слушает `process.env.PORT`);
- `SESSION_SECRET` и `ADMIN_PASSWORD` генерируются Render;
- healthcheck: `/api/health`.

Каждый push в `main` = новый релиз.

**Постоянное хранение на бесплатном плане.** Диск у бесплатных сервисов
Render эфемерный (это официально задокументировано: файлы стираются при
каждом рестарте, деплое и засыпании, persistent disk им недоступен).
Поэтому данные вынесены наружу двумя независимыми бесплатными сервисами:

- **Turso** — облачная SQLite: переменные `TURSO_URL`/`TURSO_AUTH_TOKEN`;
  проекты, статусы и администратор переживают любые рестарты;
- **Cloudinary** — файлы участников: переменная `CLOUDINARY_URL`;
  картинки/видео хранятся в облаке, в базе лежат постоянные https-ссылки.

Если переменные не задать — сервер работает по-старому, с локального диска
(удобно для разработки). Запасной вариант без внешних сервисов — платный
план Render + Persistent Disk (блок `disk` в `render.yaml`).

Перенос уже накопленных данных со старого развёртывания —
`npm run import:live -- <адрес> <логин> <пароль>`: скрипт логинится в
живой админке, забирает проекты, скачивает файлы и, при настроенном
Cloudinary, сразу заливает их в облако.

**Почему не GitHub Pages**: Pages — только статика; Express, база, сессии и
приём файлов там запустить невозможно. Pages подошёл бы только для фронта с
внешним API — то есть усложнил бы архитектуру без выгоды.

## 11. Ограничения и пути развития

Честный список того, чего **нет** (и почему):

| Ограничение | Когда понадобится | Решение |
|---|---|---|
| MemoryStore сессий (warning в логе) | второй инстанс или долгоживущий процесс | connect-sqlite3 / Postgres-стор / Redis |
| Бесплатные Turso/Cloudinary — лимиты | >5 ГБ данных или >25 кредитов файлов в месяц | апгрейд тарифа или S3-совместимое хранилище |
| Нет серверного поиска/пагинации | тысячи проектов | индекс FTS5 в SQLite + `LIMIT/OFFSET` |
| Нет e-mail уведомлений | участник должен узнавать об одобрении | nodemailer или сервис вроде Resend |
| Нет второго админа/ролей | школа с администрацией и жюри | таблица roles + policy на маршрутах |
| Нет rate-limiting на логине | публичный сервис надолго | express-rate-limit |
| Нет тестов | рост команды | Vitest (юнит фильтров/роутера) + supertest (API) |

## 12. Частые вопросы на защите

**Почему SQLite, а не PostgreSQL/MySQL?**
Объём и модель доступа: один процесс, один инстанс, сотни строк. SQLite —
файл, ноль администрирования, а та же SQL работает и в облаке (Turso/libSQL),
поэтому постоянное хранение на хостинге не потребовало ни своего сервера
СУБД, ни смены диалекта. Слой доступа изолирован за адаптером `db.js`,
поэтому миграция на PostgreSQL сводится к замене одного модуля и драйвера.

**Разве SQLite не пропадает на бесплатном Render?**
Пропадает локальный файл — это ограничение хостинга, а не базы. Решение:
приложение переключается на Turso, как только заданы `TURSO_URL` и
`TURSO_AUTH_TOKEN` (диалект и схема не меняются вообще), а файлы уходят
в Cloudinary по `CLOUDINARY_URL`. Без переменных — прежнее локальное
поведение для разработки. То есть переключение — чисто инфраструктурное,
в коде маршрутов это не отражается.

**Зачем адаптер в `db.js`, если можно было переписать запросы?**
Бэкенд писался под mysql2/promise. Адаптер эмулирует `pool.execute()` над
`@libsql/client` (~30 строк): `SELECT` → `[rows]`, пишущие →
`[{insertId, affectedRows}]`, многоблочный seed → `executeMultiple`.
Переходы MySQL → SQLite → облачная SQLite выполнялись без правок ни одного
маршрута — классический пример Anti-Corruption Layer.

**Зачем свой роутер, если есть react-router?**
Пять экранов и хэш-маршруты. Хук на `hashchange` — 40 строк без зависимостей.
react-router в зависимостях остался от более ранней версии, кандидат на удаление.

**Почему hash-маршруты (`#/catalog`), а не `/catalog`?**
Прямые ссылки на любой статик-хостинге работают без rewrite-правил; на Render
подстраховывает SPA-fallback. Цена — query-параметры парсятся вручную.

**Как хранятся пароли?**
bcrypt с cost 12: пароль + 16 байт соли → хэш `$2b$12$…`. Перебор
бесполезен, в БД нет обратимых данных. Смена пароля — правка
`ADMIN_PASSWORD` + `node server/create-admin.js`.

**Что мешает масштабированию?**
Осталось только состояние сессий (MemoryStore) — на втором инстансе сессии
не будут общими. Файлы и база уже внешние (Cloudinary, Turso), поэтому
горизонтальное масштабирование упирается только в замену хранилища сессий
на Redis/Postgres-стор. Код API при этом не меняется.

**Как защита от злонамеренных загрузок?**
Имя файла генерирует сервер (нет path traversal), фильтр mimetype,
лимиты размера/количества, отдельный каталог. Полноценный антивирусный
сканер — вне рамок проекта, упомянут как развитие.

**Откуда берётся контент страниц?**
Два источника: `content.json` (всё статичное: тексты, сцены, разделы) и
API (проекты из БД). Сайт заполняется администратором, а не программистом.

**Как это деплоится?**
`render.yaml` в репозитории + Blueprint в Render: push в `main` → сборка
`npm install && npm run build` → запуск `npm start` → healthcheck
`/api/health`. Админка и API на том же домене.

**Что с производительностью?**
Фронт — SPA, API отдаёт JSON списков до десятков килобайт; статика кэшируется
CDN(Render). Узких мест нет: лимит бесплатного плана — это сам Render
(512 МБ RAM, засыпание после простоя), а не приложение.
